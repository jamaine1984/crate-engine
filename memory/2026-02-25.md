## Deep Research Session — Game Engine Architecture

### What I Studied
- **Sketchbook** (swift502) — full Three.js game with character controller, vehicles, camera, physics
- **Ecctrl** (pmndrs) — modern React Three.js character controller with Rapier physics
- **Yuka AI** — NPC steering behaviors + state machines
- **PlayCanvas** — animation state graphs
- **Rapier** — character controller for stairs/slopes/collisions
- **KayKit bone structure** — Hand.R, LowerArm.R, 49 joints, CharacterArmature prefix
- **Knight model** — has 12 embedded animations (Idle, Walk, Run, Attack, Death, Roll, Jump, Sword attacks)
- **KayKit modular characters** — 0 animations, need external Mixamo animations

### Key Discoveries
1. Knight was NEVER a cone — it's a proper 3D model. The "avatar" procedural character was loading instead
2. Bone naming: 3 conventions (KayKit: Hand.R, Knight: MiddleHand.R, Mixamo: mixamorig:RightHand)
3. Weapon scale bug: Box3.setFromObject includes invisible bone positions (70+ units), not just mesh
4. Spring simulation is the secret sauce: `acceleration = (target - source) / mass; velocity *= damping`
5. State machines for EVERYTHING — characters, NPCs, cameras, game flow
6. Model container pattern: wrap model in Group, offset Y = -box.min.y for reliable grounding

- Fixed bone detection for all 3 naming conventions
- Restored knight as default character (has animations!)
- Weapon scale uses model.scale.x not bounding box
